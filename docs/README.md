# FitLink FE 문서

프론트엔드의 **어떻게 만드는가(HOW)**를 다룬다. 무엇을 만드는지는 [Fit-link-PRD](https://github.com/Fit-link-v2/Fit-link-PRD)에 있다.

## 구조

```
docs/
  README.md              이 문서
  architecture/          화면 전체에 걸친 규칙. 디자인 원칙 · 에러 처리
  decisions/             FE 전용 설계 결정 (FE-ADR-NNNN)
  templates/             문서 틀
  screens/               ← 현재 모습. 코드가 바뀌면 같이 고친다
    member.md            회원 화면(M-xx)의 변형 표. Figma 프레임 링크 · 근거 AC
    instructor.md        강사 화면(I-xx)의 변형 표
  spec/
    {NNNN-slug}/         ← 기록. 끝나면 동결한다
      prd.md             개발 PRD. AC 분류표 필수
      plan.md            진행 체크박스
```

- 기능 폴더 이름은 PRD 레포 폴더 이름 그대로 쓴다. 예: `spec/0003-booking/`
- 기능 하나가 여러 화면을 건드리므로 `spec/` 아래에 화면 · 도메인 폴더를 두지 않는다
- 후속 작업은 앞 폴더를 고치지 않고 새 번호 폴더를 만든다
- 그림의 원본은 Figma다. 이 레포에는 그림 설명을 쓰지 않고 링크와 표만 둔다

## 화면 ID와 변형

와이어프레임 · 시안 · story · fixture가 **같은 이름**을 쓴다.

| 대상 | 형식 | 예 |
|---|---|---|
| 화면 ID | 회원 `M-{2자리}`, 강사 `I-{2자리}`. 컴포넌트 하나에 ID 하나 | `M-02` 예약 시트 |
| 변형 | `{ID}/{변형}` 또는 `{ID}/{영역}/{변형}` | `M-02/자리 참`, `M-01/수업 줄/만석` |
| Figma 프레임 이름 | 변형 이름 그대로 | `M-01/수업 줄/만석` |
| story 이름 | 변형 이름 그대로 | `M-01/수업 줄/만석` |
| fixture 파일 | 변형이 쓰는 응답 한 벌 | `home.full.ts` |

- 처리 중 · 실패 같은 상태는 새 ID가 아니라 **변형**이다
- ID는 한 번 정하면 바꾸지 않는다. 화면을 없앨 때는 표에서 지우지 말고 "폐기"로 남긴다
- 예시 데이터는 기준 시나리오 하나를 쓴다. Figma와 fixture의 값이 같아야 대조할 수 있다
  - 오늘 = 9/9(화) 18:00, 무료 취소 마감 3시간, 회원 김OO

## AC와 테스트

| 대상 | 형식 | 예 |
|---|---|---|
| 제품 AC | `PRD-{4자리} AC {번호}` | `PRD-0003 AC 1.1.2` |
| FE 고유 AC | `FE-{4자리} AC-{번호}`. 제품 AC에 없는 조건이 생길 때만 | `FE-0003 AC-1` |
| 결정 | FE 전용은 `FE-ADR-{4자리}`, BE와 공유는 PRD 레포 `DEC-{4자리}` | `FE-ADR-0001` |

AC마다 검증 방식을 하나 정한다.

| 검증 | 대상 | 방법 |
|---|---|---|
| 테스트 | 판정 · 분기 · 문구 조립 (순수 함수 · 훅) | TDD. 테스트 이름이 AC ID로 시작한다 |
| 대조 | 배치 · 모양 · 상태별 화면 | Storybook의 변형을 시안과 나란히 본다 |

```ts
it('[PRD-0003 AC 1.1.2] 잔여가 0이면 예약 버튼을 비활성으로 두고 사유를 표시한다', () => {})
```

AC는 항상 PRD 번호까지 쓴다. PRD가 바뀌면 PR 설명의 AC ID로 이 레포를 검색해 영향 받는 화면 · 테스트를 찾는다.

## 흐름

### PRD 단위 (구현 전)

| 단계 | 산출물 |
|---|---|
| 와이어프레임 | Figma. 변형마다 프레임 하나, 노트에 근거 AC |
| 디자인 | Figma 시안 · 디자인 시스템. 와이어프레임과 같은 변형 이름 |
| 화면 표 | `screens/*.md`에 변형 · 근거 AC · 링크 추가 |

### User Story 단위 (구현)

| 단계 | 산출물 | 비고 |
|---|---|---|
| api | BE 개발 PRD의 API 절 | BE와 합의. FE는 이 모양으로 fixture를 만든다 |
| prd | `spec/{NNNN-slug}/prd.md` | AC 분류표: AC마다 테스트 / 대조 |
| plan | `spec/{NNNN-slug}/plan.md` | 승인 후 `prd.md`를 **동결** |
| go | 코드 · `plan.md` 체크박스 | 로직은 RED → GREEN → REFACTOR. UI는 변형별 시안 대조 |
| pr | doc-sync | 아래 참조 |

### doc-sync (PR 직전)

- `screens/*.md`: 구현한 변형의 "구현" 칸을 채운다
- 기능 폴더: 구현과 어긋난 설명만 고친다. 요구사항이 달라졌으면 고치지 않고 PRD 레포에 먼저 올린다
- PRD 레포 `prd.yaml`의 `specs.fe`에 기능 폴더 링크를 넣는다

머지 후 기능 폴더는 고치지 않는다.

## 링크 규칙

- 제목 앵커(`#절-이름`) 대신 파일 단위로 링크한다
- 다른 레포는 절대 URL
- Figma는 프레임(변형) 단위 노드 링크
